# الرجوعُ عن نسخةٍ — المسارُ الحقيقي

> منذ V17.81 لا يُدفَع إلى `main` مباشرةً: كلُّ شيءٍ يمرُّ بـ`staging` وبوابته. الرجوعُ إصدارٌ كغيره — يمرُّ بالمسار نفسِه فلا يُنشَر ما لم يُفحَص.

## ١ · متى نرجع
حين تكسر نسخةٌ منشورةٌ سلوكًا لا يحتمل انتظارَ الإصلاح: نموذجٌ لا يُحفَظ، شاشةٌ لا تُفتَح، أرقامٌ خاطئةٌ أمام الوزارة. الأعطالُ الصغيرةُ تُصلَح للأمام لا للخلف.

## ٢ · الخطوات
```bash
git fetch origin && git checkout main && git pull
git log --oneline -5                 # حدِّد الالتزامَ الجيّدَ الأخير
git revert --no-edit <sha-الالتزام-الكاسر>   # عكسٌ لا حذف — التاريخُ يبقى
```
ثم ختمُ نسخةٍ **أعلى** (لا إعادةُ رقمٍ قديم): وسمُ الرأس في `index.html`، و`CACHE` في `sw.js`، وسطرٌ في `RELEASE_NOTES` يقول بالعربية المبسَّطة ما أُعيد ولماذا، والسجلاتُ (`docs/api-schema.json` · `docs/system.md`) — كما في `AGENTS.md` §٤.
```bash
node scripts/check-version.mjs        # الحارسُ الكامل
git push origin HEAD:staging          # البوابةُ ثم الترقية
git fetch && git log origin/main -1   # تأكّد
```

## ٣ · ماذا يحدث على الهواتف
- `sw.js` شبكةٌ فقط: عند الفتح التالي يرى الهاتفُ عاملًا جديدًا (رقمُ كاشٍ أعلى)، يثبّت الهيكلَ الجديد، ويُعاد التحميل — كأيِّ تحديث.
- الهيكلُ من الكاش أوّلًا (V17.95): **لا يُرجَع الهاتفُ بإعادة رقمٍ قديم** — العاملُ لا يعرف «أقدم»، يعرف «مختلفًا». لذلك الرجوعُ نسخةٌ جديدةٌ برقمٍ أعلى تحمل الشيفرةَ القديمة.
- ما كُتب في الجهاز بلا شبكة يبقى في الطابور ويُرفَع بعد التحديث؛ الرجوعُ لا يمسّ البيانات.
- إن كان الكسرُ في `firestore.rules`: تُعكَس القواعدُ في الالتزام نفسِه — تُنشَر مع الوصول إلى `main` وتسري على كلِّ النسخ فورًا.

## ٤ · ما لا يُفعَل
- لا `git push --force` إلى `main` ولا إعادةُ كتابة تاريخ.
- لا تعديلٌ يدويٌّ لملفٍ على الخادم — لا خادمَ أصلًا؛ Pages ينشر ما في `main`.
- لا تخطّي البوابة: الرجوعُ الذي يسقط في الحارس ليس رجوعًا آمنًا.

## ٥ · بعد الرجوع
- يُفتَح بلاغٌ في التطبيق (صحة النظام ← البلاغات) بما كُسر، ويُكتَب سطرٌ في `docs/system.md` §١٦.
- الإصلاحُ الحقيقيُّ يُنفَّذ للأمام على `staging` بجردٍ يمنع عودتَه.
